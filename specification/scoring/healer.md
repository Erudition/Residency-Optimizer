# Schedule Healer Logic

The **Schedule Healer** corrects violations in a full "base schedule" - a raw generated schedule that may have some custom blocks locked - by performing swaps and substitutions without touching the locked blocks.

It also acts as the "Phase 2" post-generation optimization step to improve the scores of generated base schedules, while still minimizing the breaking up of the 4+1 structure.

---

## 1. Pre-Processing: Deficit Recovery
Before starting simulated annealing, the healer runs a targeted **Deficit Recovery** step specifically designed for split blocks that are prone to fragmentation:
*   **Target Rotations:** `NEURO`, `GI`, and `PULM`.
*   **Mechanic:** For any resident identified by the RequirementsEngine as having a deficit in these target rotations, the healer replaces unlocked `ELECTIVE` weeks with the missing rotation until the deficit is recovered or no more flexible weeks exist.
*   **Goal:** Provides a valid baseline of required assignments so that subsequent annealing phases can swap them around to resolve staffing violations rather than struggling to find where to add them.

---

## 2. Core Simulated Annealing Solver
The core of the Healer is a Simulated Annealing algorithm that iteratively optimizes the entire multi-year schedule grid.

### Seeded Deterministic RNG
To ensure reproducibility during schedule generation, the solver uses a custom LCG (Linear Congruential Generator) seeded based on the current attempt index:
```typescript
class SeededRNG {
    private seed: number;
    constructor(seed: number) { this.seed = seed; }
    next(): number {
        this.seed = (this.seed * 9301 + 49297) % 233280;
        return this.seed / 233280;
    }
}
```

### Flexibility Constraint Check
Only specific blocks can be manipulated by the Healer. A resident's week is considered **flexible** and candidate for swapping if and only if:
1.  The week falls within the resident's active range (`activeWeekStart` to `activeWeekEnd`).
2.  The week **does not** belong to the resident's clinic cohort (complying with the 4+1 Golden Rule).
3.  The week is not explicitly locked (e.g., pre-approved vacation requests).

---

## 3. Penalty Cost System
The Healer evaluates the schedule quality using a hierarchical penalty scoring system. Minimizing this global penalty is the optimization objective:

| Weight Name | Penalty Value | Description / Trigger Condition |
| :--- | :---: | :--- |
| `W_STAFFING` | **$10,000,000$** | Triggered when weekly rotation assignments violate minimum/maximum interns or seniors defined in `ROTATION_METADATA` (e.g., understaffing MICU, overstaffing Wards). |
| `W_JEOPARDY` | **$5,000,000$** | Triggered if a week has fewer than **1 PGY-2** OR fewer than **1 PGY-3** available on flexible assignments (`ELECTIVE` or `AMCS_CONSULTS`) to cover jeopardy calls. |
| `W_REQUIREMENT` | **$25,000$** | Triggered for every week of deficit in core educational requirements or ACGME minimum distributions for the resident's level. |
| `W_CONTINUITY` | **$1,000$** | Triggered for each assignment change within a 5-week block cycle. Lower values encourage contiguous block assignments. |

---

## 4. The Annealing Loop
The optimization runs for a budget of **$200,000$ steps** with a starting temperature of `1.0` and a cooling factor of `0.99998` per step:

### Block Size Selection
The healer swaps contiguous blocks of weeks (not just single weeks) to maintain block-based schedules. The block size decreases as the algorithm progresses:
*   **Early Phase (<50% progress):** $70\%$ chance of $4$-week blocks, $20\%$ chance of $2$-week blocks, $10\%$ chance of $1$-week blocks.
*   **Mid Phase (50% - 80% progress):** $30\%$ chance of $4$-week blocks, $40\%$ chance of $2$-week blocks, $30\%$ chance of $1$-week blocks.
*   **Late Phase (>80% progress):** $10\%$ chance of $4$-week blocks, $30\%$ chance of $2$-week blocks, $60\%$ chance of $1$-week blocks.

### The Metropolis Acceptance Criterion
At each step, a candidate swap is generated by assigning a random valid rotation to a chosen block of flexible weeks for a resident. The resulting change in penalty ($\Delta = \text{newPenalty} - \text{oldPenalty}$) is calculated:

1.  **Improvements ($\Delta \le 0$):** The swap decreases or maintains the penalty. **Always accepted**.
2.  **Degradations ($\Delta > 0$):** The swap increases the penalty. Accepted **probabilistically** based on the current temperature to escape local minima:
    $$P(\text{acceptance}) = e^{-\frac{\Delta}{temp \times 25,000}} > \text{random}()$$

---

## 5. Elitism & No-Degradation Guarantee (Elitism)
To ensure the healer never discards the highest-quality schedule or returns a degraded schedule compared to the input base:
*   **Best Caching:** The healer maintains a `bestSchedule` and a `bestPenalty` tracking variable.
*   **Live Updates:** Every time a swap is accepted, if the resulting `currentPenalty` is strictly lower than `bestPenalty`, the solver captures a deep copy of the schedule and updates `bestPenalty`.
*   **Final Recovery:** At the end of the $200,000$ steps, the solver restores and returns `bestSchedule`. This ensures that even if simulated annealing accepted a worse state near the end of its run due to high temperature or got stuck in a local minimum, the final returned schedule is the absolute best state ever encountered.
